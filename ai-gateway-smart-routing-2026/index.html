核心结论

智能模型路由不是再增加一种 Provider 排序策略，而是在现有路由之前增加模型能力决策层。

01边界要清楚现有路由解决“同一模型由谁执行”；新增能力解决“本次到底该使用哪个模型档位”。
02预测成功概率目标是 P(success | request, model)，而不是给请求贴一个脱离业务损失函数的“简单/困难”标签。
03MVP 只做两档efficient 与 capable 足以验证收益；三档会显著增加阈值和评测复杂度。
04确定性级联硬约束和规则先行，仅对 uncertain 请求调用 Classifier；任何异常默认 capable。
05按成功任务核算Router、Judge、重试、跨档 Fallback、缓存损失与人工接管都必须计入成本。
推荐起点显式虚拟模型 model:auto + 两档模型 + 规则级联 + uncertain Classifier + task-sticky + observe-only + 强模型兜底。Stage Router 放到第二阶段。

第一性原理：优化“成功任务成本”

Prompt 长度、是否包含代码只能作为特征；真正的约束是不同模型在当前任务上的成功概率。

候选集合： Mᵉ(x) = { m | modality ∧ context ∧ tools ∧ protocol ∧ region ∧ policy }
质量约束： P(success | x, m) ≥ Qmin
模型选择： m* = argmin E[WorkflowCost(m | x)]

成功概率

针对当前请求、模型版本和业务成功标准估计，不能把模型永久贴成“强/弱”。

工作流成本

模型调用 + Router + Judge + 重试 + Fallback + 缓存损失 + 工具失败 + 人工接管。

损失函数

普通摘要和生产变更的错误代价不同；高风险任务应提高质量下限或直接固定 capable。

净收益条件

α · (Cstrong − Cefficient) > Crouter + Cretry/fallback/cache-loss
不要把“小模型占比”当北极星即使账单下降，如果错误降级带来更多重试，Cost per Successful Task 仍可能上升。

附件案例：Switchyard × Deep Agents

附件提供了轨迹级路由案例；其中数字应按厂商集成评测而非行业基准理解。

145多步 Agent 任务
93%回合交给 30B 高效模型
7%回合交给 Claude Opus 4.8
≈70%报告称总成本下降
数字的正确读法约 90% 的 Opus 准确率保留来自特定 Harness、145 个任务和特定模型组合，尚无完整任务明细、置信区间与独立复现，不能直接外推为 TokenHub 的收益承诺。

Stage Router：难度是运行状态

WRONG → capable

  • 窗口内错误严重度升高
  • 长时间 churn、没有读写进展
  • 持续读取和规划但不产出
  • 关键测试失败或严重错误
  • 上下文压缩、恢复和卡住

PROGRESS → efficient

  • 近期持续写入或编辑
  • 进入机械实现阶段
  • 修改范围和计划明确
  • 测试通过且无窗口错误
  • 格式化、总结、重跑和收尾

Switchyard 将多种信号组合后通过 tanh 压缩为 0～1 的置信度；严重错误可硬升级。官方起始阈值 0.5 来自 SWE-Bench Pro Python-75 校准，不应原样复制到其他业务。

三类 Router 的失败语义

Router判断时点正常行为判断失败时TokenHub 建议
Capability Classifier请求开始前依据 p_solve 和 capability boundary 选强/弱无效或不可解析 verdict → strongMVP 默认语义
Stage RouterAgent 回合前轨迹信号明确时改变档位信号不明确 → picker 默认档位高风险项目设置 capable 下限
Escalation高效模型完成后缓冲结果，Judge 连续确认后锁定 strongJudge 失败 → 返回弱模型缓冲结果仅低风险、可验证任务允许
生产边界Switchyard 官方仍标注 pre-alpha / experimental / not for production use。TokenHub 应借鉴算法、事件模型与 Eval 方法，而不是固化其当前 API。

推荐的 TokenHub 分层架构

智能 Router 只返回语义目标；凭证、目标白名单、执行、重试、计费和审计继续由 TokenHub 掌握。

现有Auth / Preliminary Admission / Guardrail校验调用者、虚拟模型访问、IP、请求体和内容安全

6.2 同步请求时序

0
Gateway 入口
解析协议并完成预校验：API Key、Project、IP、请求体上限；识别具体模型还是虚拟模型。
Guardrail block、无效请求和未授权请求在此终止，不调用 Router。
1
访问与安全
检查虚拟模型访问 + 执行内容安全，为 Classifier 构造脱敏后的标准化 RouterInput。
Classifier 不应看到本地 mask 规则已识别的原始敏感值。
2
Policy Resolver
解析有效策略：沿用 API Key → Project → Global 优先级；同一 Scope 多绑定按 conflict 失败。
建议新建 smart-routing-policies AdminResource kind。
3
Candidate Builder
生成 efficient / capable 候选，同时检查实际模型访问权和 Model 元数据硬约束。
调用者既要有 auto 模型权限，也必须有最终目标模型权限。
4
Smart Resolver
Session 命中 → 复用；否则 Constraint → Rule → Classifier，产出 observed target。
Classifier 使用 concrete model，并设置 internal_router_call 防止递归。
5
Mode Switch
observe_only：记录 observed target，但 actual target 固定 capable；enforce：actual = observed。
同一决策同时保存策略版本，确保回放可复现。
6
Existing Admission
使用 actual model 估算 Token / 价格并进入现有 StartCall，完成 TPM、成本与并发预留。
为避免 Router 成为免费放大器，分类前另设轻量 Router RPM / Budget。
7
Existing Routing
调用 SelectRouteCandidates(actualModel)，继续执行 Scoped Policy、Adaptive、Affinity、Breaker 与 Provider Failover。
L1 不直接持有 Provider Credential，也不构造任意 Endpoint。
8
Settlement
流式/缓冲返回并结算实际 Usage；RouterDecisionLog 关联 Request、Attempts 和最终业务 Outcome。
请求日志同时保留 requested_model、observed_model 和 actual_model。

6.3 核心 Go 接口与决策伪代码

type ModelRouter interface {
    Resolve(ctx context.Context, in ResolveInput) (RouterDecision, error)
}

type ResolveInput struct {
    RequestID      string
    RequestedModel string
    Project        Project
    APIKey         APIKey
    Envelope       RequestEnvelope
    AgentContext   *AgentRoutingContext
    Policy         CompiledSmartRoutingPolicy
    Now            time.Time
}

type RouterDecision struct {
    PolicyID       string
    PolicyVersion  int64
    Mode            string
    Tier            string
    ObservedModel   string
    ActualModel     string
    Source          string
    Confidence      float64
    ReasonCodes     []string
    RouterUsage     RouterUsage
    FallbackReason  string
}
if !isVirtualModel(req.Model) && !policy.OptInConcrete {
    return passthrough(req.Model)
}

policy := effectivePolicy(apiKey, project, global)
candidates := buildTiers(policy, modelCatalog, access)

if b := sessionStore.Get(sessionKey); b.Valid(policy.Version) {
    return applyMode(b.Decision, policy.Mode)
}
if d := hardConstraints(candidates, request); d.Decided {
    return persist(applyMode(d, policy.Mode))
}
if d := rules.Evaluate(request, agentContext); d.Decided {
    return persist(applyMode(d, policy.Mode))
}

d := classifier.Predict(sanitizedInput)
if d.Invalid || d.PSolve < threshold(d.Boundary) {
    d = capable("classifier_fallback")
}
return persist(applyMode(d, policy.Mode))
不递归Classifier 必须指向 concrete model，内部调用显式绕过 L1，但继续经过 TokenHub L2。
不越权策略中的 Tier 模型不能绕过 Project / API Key 的模型访问交集。
不信任客户端降风险客户端 Agent Context 可以触发升级；只有可信 SDK 签名或服务端事件才能触发降级。
不丢失原请求跨档重试始终从不可变原始请求重新构造，不能沿用已被 Provider 改写的 payload。

6.5 协议、流式与后台任务语义

场景推荐语义原因
Chat / Responses / MessagesMVP 首批支持；先统一成 RequestEnvelope，再做 L1 决策。三类请求包含任务语义，且能映射到现有 Provider Adapter。
Embeddings / Image / count_tokensMVP 不启用智能模型路由，只保留现有显式模型路由。能力维度和计费语义不同，避免一次扩展过宽。
StreamingClassifier 和跨档选择必须在首字节前完成；输出开始后禁止透明切换模型。流式响应无法安全撤回，现有 TokenHub 也不能在输出后切换 upstream。
Escalation仅 stream=false 或显式缓冲模式；不进入第一版。弱模型 + Judge + 强模型会增加尾延迟和重复成本。
Background Responses提交时冻结 policy id/version；Worker 获得 fenced lease 后做 L1 决策并在 Provider dispatch 前持久化。保证重启、重复 claim 和策略更新时可审计、可复现。
Agent Stage要求 session_id + turn_id + revision；乱序回合不得覆盖更新状态。多实例和并发工具回合下必须保持单调状态。

6.6 失败语义与跨档兜底

失败点默认处理是否调用 Provider记录原因
没有有效策略 / 同 Scope 冲突虚拟模型请求 fail closed；返回明确 smart_routing_policy_unavailable / conflict否policy_missing / policy_conflict
Classifier 超时、429、无效 JSON、空 content选择 capable；不把判断错误暴露成业务失败调用 capableclassifier_timeout / invalid_verdict
Session Store 不可用task-sticky 请求默认 capable；禁止悄悄变成每回合随机决策调用 capablesession_store_unavailable
efficient 无可用 Provider / 所有 retryable attempt 失败在首字节前按策略最多跨档到 capable 一次可调用 capableexecution_fallback_to_capable
上游已输出首字节后失败保持现有流式错误语义，不跨模型重放不再调用stream_started_no_cross_tier_retry
请求 4xx、Guardrail、Quota、权限失败直接返回，不触发 Classifier 或跨档兜底否沿用原错误码
跨档兜底不是“第二套普通 Failover”只允许 retryable、首字节前、幂等请求，并设置单次上限；否则错误路由会变成双倍调用和不可控尾延迟。

6.7 控制面与运行时 API

GET/POST /api/admin/smart-routing-policies

策略 CRUD、Scope 绑定、版本、状态和审计；权限模型沿用 Routing Policy。

POST /api/admin/smart-routing-policies/{id}/simulate

输入请求样例，返回 Constraint、Rule、Classifier 和最终决策解释，不真实调用业务模型。

POST /api/admin/smart-routing/replay

针对历史 RequestLog 离线回放新策略，输出选择变化和预计成本，不影响线上。

POST /api/router/feedback

Agent Harness 或业务系统按 request_id 回传 task success、测试、人工接管等结果；幂等写入。

x-tokenhub-routing-session-id

可作为 metadata 的协议无关补充；不得包含原始敏感信息，服务端仅保存哈希。

x-tokenhub-selected-model

控制面策略契约

不要把智能模型路由塞进现有 ModelRoute 的 strategy 字段；建立独立、可版本化、可审计的策略对象。

SmartRoutingPolicy

定义虚拟模型、模式、Tier、端点范围、Classifier、Session 与跨档兜底。

disabled | observe_only | enforce

AgentRoutingContext

由 Agent SDK 提供结构化轨迹；未经签名的客户端字段只允许触发升级。

评测体系：先证明，再放量

Router 分类准确率不是最终答案，必须比较完整工作流的质量、成本与延迟。

capable-only

全部使用强模型，提供质量上限、基线成本和轨迹信号。

efficient-only

全部使用高效模型，识别安全下放范围和能力边界。

routed

应用真实策略，测量 Router 开销、错误路由、Fallback 和缓存变化。

模型互补四象限

SAFE

强模型通过，高效模型也通过

最适合安全降级。

LOSS

强模型通过，高效模型失败

最关键的错误降级象限，必须重点压低。

RESCUE

强模型失败，高效模型通过

说明模型存在互补，不能只按总榜单排序。

HARD

两个模型都失败

应改进 Harness、工具、上下文或引入人工。

风险、反模式与明确边界

模型路由减少单模型依赖，但会增加协议、轨迹、缓存、评测和策略治理复杂度。

协议能力不等价

system / developer message、tool schema、structured output、reasoning field 和 streaming event 不能只靠替换 model ID。

缓存与上下文连续性

跨模型可能降低 Prompt Cache 命中；强模型接手时还要理解高效模型留下的轨迹。

工具副作用

支付、删除、发布等不可逆工具应固定 capable 或人工门禁，不能依赖事后 Escalation。

Classifier 漂移

模型版本、流量和价格变化都会改变阈值；策略必须按版本记录并定期回放。

计费语义

必须明确按 virtual model 还是 actual model 计价，并同时保留 Provider 实际成本，避免账单不可解释。

不要承诺 70% 降本

附件数字依赖特定 Harness、任务和模型组合；TokenHub 必须用自身流量重新测量。

默认安全选择Classifier JSON 无效、Router 超时、目标协议不兼容、Session 不可用或低置信时选择 capable；虚拟模型没有有效策略时 fail closed，而不是随机选择模型。
