核心结论

智能模型路由不是再增加一种 Provider 排序策略，而是在现有路由之前增加模型能力决策层。

01边界要清楚TokenHub 现有路由解决“同一个模型由谁执行”；新增能力解决“这次到底该用哪个档位的模型”。
02不要预测抽象难度真正需要估计的是 P(success | request, model)，并选择达到质量下限的最低成本模型。
03MVP 只做两档efficient 与 capable 足够验证价值；三档会显著增加标注、阈值和评测复杂度。
04先规则后分类器硬约束和高置信规则零成本处理，仅对不确定请求调用轻量 Classifier。
05以成功任务成本为准小模型占比不是目标；Router、失败重试、Fallback、缓存损失与人工修复都要计入。
推荐起点显式虚拟模型 model:auto + 两档模型 + 规则级联 + 不确定请求分类 + task-sticky + observe-only + 强模型兜底。Agent Stage Router 放到第二阶段。

第一性原理：优化“成功任务成本”

Prompt 长度、是否包含代码等只能作为特征，不能等同于难度；模型路由应直接面向任务成功概率。

候选集合： Mᵉ(x) = { m | modality ∧ context ∧ tools ∧ protocol ∧ region ∧ policy }
质量约束： P(success | x, m) ≥ Qmin
模型选择： m* = argmin E[WorkflowCost(m | x)]

成功概率

针对当前请求、当前模型版本和当前业务成功标准估计，而不是给模型贴一个永久“强/弱”标签。

工作流成本

模型调用 + Router + Judge + 重试 + Fallback + 缓存损失 + 工具失败 + 人工接管。

损失函数

普通摘要和生产变更的错误代价不同。高风险任务应提高质量下限，甚至直接固定 capable。

什么时候智能路由才真正省钱？

净收益条件： α · (Cstrong − Cefficient) > Crouter + Cretry/fallback/cache-loss
不要把“小模型请求占比”当北极星即使账单下降，如果错误降级导致成功率下降、重试变多，Cost per Successful Task 可能反而上升。

附件案例：Switchyard × Deep Agents

附件提供了一个很好的轨迹级路由案例，但其中数字必须按厂商集成评测而非行业基准理解。

145多步 Agent 任务
93%回合交给 30B 高效模型
7%回合交给 Claude Opus 4.8
≈70%报告称总成本下降
数字的正确读法附件同时指出：约 90% 的 Opus 准确率保留来自特定 Harness、145 个任务和特定模型组合，尚未看到完整任务明细、置信区间与独立复现，因此不能直接外推为 TokenHub 的收益承诺。

Stage Router 把“难度”从 Prompt 属性变成运行状态

WRONG → capable

  • 窗口内错误严重度升高
  • 长时间 churn、没有读写进展
  • 持续读取和规划但不产出
  • 关键测试失败或严重错误
  • 上下文压缩、恢复和卡住

PROGRESS → efficient

  • 近期持续写入或编辑
  • 已进入机械实现阶段
  • 修改范围和计划明确
  • 测试通过且无窗口错误
  • 格式化、总结、重跑和收尾

Switchyard 将多种信号组合后通过 tanh 压缩为 0～1 的置信度；严重错误可硬升级。官方文档给出的起始阈值是 0.5，但该值来自 SWE-Bench Pro Python-75 校准，不应原样复制到其他业务。

三类 Router 的失败语义并不相同

Router判断时点正常行为判断失败时的官方行为TokenHub 建议
Capability Classifier请求开始前依据 p_solve 和 capability boundary 选强/弱无效、矛盾或不可解析 verdict → strong作为 MVP 的默认安全语义
Stage Router每个 Agent 回合前轨迹信号明确则改变默认档位信号不明确且无 Classifier → picker 默认档位高风险项目默认 capable-first 或显式风险下限
Escalation高效模型完成后缓冲弱模型结果，Judge 连续确认后锁定 strongJudge 失败 → 返回已缓冲的弱模型结果并保持 streak仅在低风险、可验证任务中允许 fail-open
生产边界Switchyard 官方仍将项目标为 pre-alpha / experimental / not for production use。TokenHub 应借鉴算法、事件模型和评测方法，而不是把其当前 API 直接固化为长期生产依赖。

评测体系：先证明，再放量

Router 分类准确率不是最终答案，必须比较完整工作流的质量、成本与延迟。

capable-only

全部使用强模型，提供质量上限、基线成本与轨迹信号。

efficient-only

全部使用高效模型，识别安全下放范围和能力边界。

routed

应用真实策略，测量 Router 开销、错误路由、Fallback 和缓存变化。

四象限不是“难度标签”，而是模型互补关系

SAFE

强模型通过，高效模型也通过

最适合安全降级；用于建立成本节省基本盘。

LOSS

强模型通过，高效模型失败

最关键的错误降级象限，必须重点压低。

RESCUE

强模型失败，高效模型通过

说明模型存在互补，单纯以“强弱”排序会遗漏收益。

HARD

两个模型都失败

应改进 Harness、工具、上下文或引入人工，而不是只调整阈值。

核心指标

Cost per Successful Task北极星指标
Task Success Rate最终任务成功而非 HTTP 200
False Downgrade Rate错误下放导致失败
Unnecessary Upgrade高效模型可完成却调用强模型
Router Cost RatioRouter 成本 / 总模型成本
Fallback / Retry Tokens错误路由浪费
Cache Hit Delta跨模型切换的缓存影响
P95 End-to-End Latency含判断和重试

风险、反模式与明确边界

模型路由减少单模型依赖，但会增加协议、轨迹、缓存、评测和策略治理复杂度。

协议与能力不等价

不同模型对 system / developer message、tool schema、structured output、reasoning field 和 streaming event 的支持不同，不能只替换 model ID。

缓存与上下文连续性

跨模型可能降低 Prompt Cache / KV Cache 命中；强模型接手时还要理解高效模型留下的轨迹。

工具副作用

高效模型已经执行支付、删除或发布后再升级，无法简单“重做”。不可逆工具应固定 capable 或人工门禁。

Classifier 也会漂移

模型版本、业务流量和价格变化都会改变最佳阈值。策略必须按版本记录并定期回放校准。

不要隐式降级具体模型

会破坏客户预期、可复现性和计费解释。优先使用显式虚拟模型或项目明确授权。

不要直接承诺 70% 降本

附件数字依赖特定 Harness、任务和模型组合；TokenHub 需要用自身流量和失败成本重新测量。

默认安全选择分类 JSON 无效、Router 超时、目标协议不兼容、候选不足、策略冲突或低置信时，返回 capable 档位；低风险业务若选择 fail-open，必须显式配置并完整审计。
