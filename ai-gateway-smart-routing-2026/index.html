核心结论

当前 TokenHub 基础路由不需要第三方模型；本方案只在确定性方法无法判断时，选择性调用一个决策模型。

01当前实现不依赖 LLM 决策现有路由主要依据模型名、策略、权重、成本、质量、成功率和延迟选择 Provider / Resource。
02第三方模型是可选层硬约束与规则输出 uncertain 时，Classifier 才预测高效模型的 p_solve。
03模型不直接控制流量决策模型只返回结构化证据；TokenHub 应用阈值、风险下限和 Allowlist 得出最终目标。
04数据边界优先默认发送脱敏、裁剪后的 RouterInput；高敏场景可关闭第三方调用或使用自托管模型。
05判断失败走 capable超时、429、无效 JSON、空 content 或低置信都不能把业务请求留在低档模型。
推荐 MVPmodel:auto + efficient / capable 两档 + Constraint + Rule / Stage Signal + task-sticky + observe-only + capable 兜底。第三方 Classifier 只在后续阶段处理低置信、歧义区间，不是首版必经路径，也不能选择任意 Provider Endpoint。

第一性原理：优化成功任务成本

请求长度和关键词只是特征，最终应估计不同模型完成当前任务的概率。

候选集合： Mᵉ(x) = { m | modality ∧ context ∧ tools ∧ protocol ∧ policy }
质量约束： P(success | x, m) ≥ Qmin
模型选择： m* = argmin E[WorkflowCost(m | x)]

成功概率

由规则、历史样本或决策模型估计，必须按模型版本和业务类型校准。

工作流成本

业务模型 + 决策模型 + Judge + 重试 + 跨档 Fallback + 缓存损失。

任务损失

不可逆写入、安全修复和监管任务应提高 Qmin，甚至固定 capable。

净收益条件安全下放收益 > Router 模型成本 + 错误路由成本 + 缓存与重试损失。因此决策模型不能对所有请求无差别调用。

推荐的决策级联

第三方模型只负责确定性方法留下的 uncertain 流量。

① Constraint不支持 Tool / Context / 协议 → capable 或排除
→
② Risk Rules安全、高风险、不可逆工具 → capable
→
③ Easy Rules抽取、格式化、机械修改 → efficient
→
④ Classifier仅 uncertain；输出 p_solve 与边界
→
⑤ Policy阈值、风险下限、Session 与 observe/enforce
默认

Rules-only

不调用任何第三方模型，成本与数据风险最低；适合流量稳定、任务类型清晰的场景。

Phase 2

Capability Classifier

请求开始前预测高效模型能否完成整个任务；判断异常默认 capable。

Agent

Stage Router

结构化轨迹先打分，只有信号不明确时再调用 Classifier 打破平局。

后期

Escalation Judge

高效模型完成后，由 Judge 评估是否升级；仅适用于可缓冲、可重试、无副作用任务。

离线

Router Trainer / Eval

可用第三方强模型生成弱监督标签，但线上策略必须使用独立测试集验证。

不建议

LLM 直接选 URL

模型不能持有凭证、构造 Endpoint 或绕过 Allowlist；它只返回语义判断。

附件案例：Switchyard 的模型决策

附件明确包含 LLM Classifier 与 Escalation Judge，因此第三方模型参与决策是可参考路径，但并非 Stage Router 的全部。

145多步 Agent 任务
93%回合交给 30B 模型
7%回合使用 Opus
≈70%报告称成本下降

哪些环节调用模型做决策？

请求开始前

LLM Capability Classifier

返回 p_solve、capability boundary、primary rule 与 crux；确定性阈值再决定 strong / weak。

轨迹信号不明确时

Stage Tie-breaker

Stage Router 主要读取 tool-result history；可配置 Classifier 处理低置信回合，并非每回合必调。

高效模型完成后

Escalation Judge

Judge 评估持续错误、循环或漂移；达到连续确认条件后把 Session 锁定到强模型。

轨迹直接升级

  • 严重错误
  • 持续 churn、没有读写
  • 只探索不产出
  • 关键测试失败

轨迹允许降档

  • 持续写入或编辑
  • 计划与范围明确
  • 测试通过
  • 机械实现与收尾
正确解读附件也强调无效 Classifier JSON、Judge 失败、协议不兼容和低置信要有 trusted fallback，并先运行 observe-only；145 项结果不能直接作为 TokenHub 的收益承诺。

推荐的 TokenHub 分层架构

第三方决策模型通过 TokenHub 受控调用，不能成为旁路控制平面。

现有Auth / Preliminary Admission / Guardrail校验调用者、虚拟模型访问、IP 和内容安全
新增Smart Model ResolverConstraint → Rules → optional Classifier / Judge → deterministic policy
复用Internal Classifier Call + Existing L2决策模型使用 concrete model，绕过 L1 但继续经过 Provider 路由、配额和审计
复用Actual Model Admission + Route Planner按业务 actual model 预留 Token / 成本，再选择 Provider / Resource
扩展Decision Log / Usage / Outcome Feedback分别核算 Router 与业务模型成本，关联最终任务结果
凭证仍归 TokenHub决策模型看不到 Provider API Key，也不能返回自定义 Endpoint。
Concrete model 防递归Classifier 配置不能引用 auto；内部调用标记 internal_router_call。
业务访问权不被绕过调用者必须同时有虚拟模型和最终 actual model 的权限。
决策模型结果不可信JSON Schema 校验、阈值和风险规则始终在本地确定性执行。

第三方决策模型：角色、部署与数据边界

有使用，但应当是可关闭、可替换、可计量的辅助组件，而不是所有请求的强依赖。

现状与方案要区分TokenHub 当前基础 Provider 路由没有通过第三方 LLM 阅读问题并选模型；以下内容是智能路由新增方案。决策模型可以来自外部 Provider，也可以是内部 vLLM、Kronk 或其他 OpenAI-compatible 服务。

6.1 决策权如何划分

TokenHub 本地预处理脱敏、特征提取、硬约束、风险规则和候选模型卡
→
第三方 / 自托管模型只输出 p_solve、boundary、crux、置信度或 escalate / decline
→
TokenHub 确定性 PolicySchema 校验、阈值、风险下限、Allowlist、Session 与 fallback
核心原则第三方模型提供的是“证据”，不是“执行命令”。最终选择只能落在策略预先声明的 Tier 和具体模型集合中。

6.5 决策模型选择标准

结构化输出稳定性

JSON Schema 成功率比通用榜单更重要；空 content 或截断 Verdict 必须被监控。

校准能力

p_solve 要在 TokenHub 自身任务上做 reliability curve / Brier Score 校准。

成本与时延

Classifier 的 P95 和单次成本应显著低于强弱模型价差；只判断 uncertain 流量。

版本稳定性

固定具体版本，模型升级触发新的 Policy Version 和 Replay，不静默漂移。

数据与地域

Provider、Region、保留策略和训练使用条款必须满足项目的数据边界。

独立性

可考虑与 capable 模型不同供应商，避免同一 Provider 故障同时影响判断与执行；也要衡量额外锁定。

6.6 成本、配额与可用性

控制项建议
内部身份建立专用 Router System Project / API Key；不复用业务调用者凭证。
路由配额独立 RPM、TPM、并发和日 / 月成本上限；避免 Router 成为免费调用放大器。
Timeout设置较短硬超时；超时直接 capable，不阻塞业务链路等待重试风暴。
缓存可按 policy version + classifier version + sanitized task hash 缓存 task-sticky Verdict；不得跨租户共享。
健康决策模型不可用时自动绕过 Classifier 并选择 capable；不要让业务整体 503。
成本归属Router Usage 单独记账，可选择平台承担或按 Project chargeback，但必须与业务模型成本分开显示。

TokenHub 运行时设计

关键插入点是 Guardrail 之后、业务模型 StartCall 之前；决策模型自身走一条受控的内部调用链。

7.1 同步请求时序

0
Gateway 入口
解析请求并预校验：API Key、Project、IP、请求体、虚拟模型访问。
无效请求不调用任何 Router 模型。
1
Guardrail
内容安全和脱敏，生成不可变原始业务请求与 Sanitized RouterInput。
外部 Classifier 只读取允许字段。
2
Policy
API Key → Project → Global 解析 SmartRoutingPolicy，构建 Tier 候选并检查实际模型访问权。
同 Scope 多绑定 conflict；虚拟模型无策略 fail closed。
3
Local Decision
Session → Constraint → Risk Rule → Easy Rule，有明确结果则跳过 Classifier。
应记录 decision_source。
4
Internal Classifier
仅 uncertain 调用 concrete decision model：使用 Router System Project，经 TokenHub L2 选择 Provider。
设置 bypass L1，防止 auto → classifier → auto 递归。
5
Deterministic Policy
校验 Verdict + 应用阈值 / 风险下限，得到 observed model；observe_only 时 actual 固定 capable。
保存 classifier model / provider / version / cost。
6
Business Admission
按 actual model 进入现有 StartCall，完成 TPM、成本与并发预留。
Router 成本已由独立内部调用结算。
7
Existing Route
SelectRouteCandidates(actualModel) → Scoped Policy → Provider / Resource → Failover。
L1 不修改现有候选算法。
8
Settlement
返回业务响应并结算 Usage；DecisionLog 关联 Router Call、Business Call、Attempts 与 Feedback。
同时保留 requested / observed / actual model。
