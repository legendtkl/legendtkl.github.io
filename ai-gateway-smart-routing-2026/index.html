核心结论

智能路由不是一个“神奇分类器”，而是一套分层的约束优化与反馈控制系统。

01先分层，再谈智能选模型、选供应商/区域、选推理实例是三个不同问题；一个产品常常只覆盖其中一层。
02硬约束先于打分协议、模态、工具、上下文、地域合规和健康状态不满足时，模型质量再高也不能入选。
03简单基线往往很强规则、意图映射与域内 kNN 可能优于复杂路由器，不应跳过。[S36]
04优化工作流成本Agent 的重试、缓存失效与升级调用会让真实成本偏离 Token 标价。[S43]
05混合架构更实用网关做协议、治理和容灾；独立 Router 做模型决策；推理网关做 KV Cache 感知调度。
一句话定义AI Gateway 智能路由 = Policy Engine（可用性与合规） + Model Performance Estimator（按请求预测效果） + Traffic Controller（供应商与实例调度） + Feedback Loop（持续校准）。

第一性原理：究竟在路由什么？

“Smart Routing”常被营销成一个概念，但生产系统至少存在三层路由对象。

L1 · 模型选择
问题：这条请求应该交给哪个模型或 Agent？
信号：任务类型、复杂度、领域、模态、工具、质量预测、成本预算
决定能力与单位经济性
L2 · 供应商/部署
问题：同一个模型走哪个 Provider、区域、账号、Key 或部署？
信号：价格、健康度、限额、延迟、地域、数据驻留、缓存粘性
决定可用性与交付稳定性
L3 · 推理实例
问题：自建模型请求落到哪个 Pod、GPU、LoRA Adapter？
信号：队列、GPU/KV Cache、前缀命中、Adapter 可用性、负载
决定 TTFT、吞吐与利用率
边界判断Google Cloud API Gateway 当前公开预览主要读取请求中的 model 字段做规则映射，这属于显式路由，并非按内容自动选择模型。[S04] Vercel、Helicone、Envoy 更偏 L2；Kubernetes Inference Extension 与 AIBrix 更偏 L3。[S25][S26][S27][S28][S29]

可落地的数学表达

候选过滤： Mᵉ(x) = { m ∈ M | protocol ∧ modality ∧ context ∧ tools ∧ region ∧ policy ∧ healthy }

预测效用： U(m|x) = wq·Q̂(m,x) − wc·Ĉ(m,x) − wl·L̂(m,x) − wr·R̂(m,x) + wh·Ĥcache(m,x) + β·Uncertainty(m,x)

选择： m* = argmax U(m|x)，同时满足 E[cost] ≤ budget、P(SLA) ≥ target

Q̂ · 任务成功概率

不是预测抽象的“模型强弱”，而是当前请求、当前模型版本、当前业务指标下的成功概率。

Ĉ · 真实工作流成本

输入、输出、缓存、Router、重试、Fallback、工具失败和人工复核都应纳入。

L̂ / R̂ / Ĥ

使用 TTFT、TPOT、排队、错误率、限额和 Cache 命中，而不是只看平均总时延。

意图 / 语义路由

用 Embedding、关键词或小模型识别领域与任务，再匹配专用模型或工作流。

本地向量低；远程模型高

优势

陷阱

复杂度分类器

根据长度、代码、推理词或轻量分类模型，分为 simple / medium / reasoning。

开销

数据
阈值或少量标注
优势
快速形成强弱模型梯度
陷阱
长度不是难度，多轮易误判
L3

质量 / 偏好预测器

学习 P(model A 优于 B | prompt)，或直接预测每个候选的任务效用。

开销
小模型或 kNN 检索
数据
候选响应 + 评价/偏好
优势

陷阱
标注昂贵、版本漂移、离线偏差
L3

级联 / 自验证

先用便宜模型生成；若置信度或 Verifier 不通过，再升级到强模型。

开销
失败样本增加调用
数据
验证器、置信度或阈值
优势
能看到实际输出后再决定
陷阱
尾延迟高，错误上下文会污染升级
L4

Contextual Bandit / 在线学习

把模型视作 Arm，在预算和风险约束下探索，利用真实反馈持续更新。

开销
决策低，但需反馈管道
数据
可从部分反馈逐步学习
优势
适应模型、价格和流量漂移
陷阱
探索有业务风险，奖励稀疏延迟
Agent

任务级 / 步骤级路由

Agent 可在任务入口固定模型，也可按检索、规划、编码、验证步骤分别路由。

开销
取决于粒度
数据

优势

重试并非总是安全

首个 Token 输出前通常仍可换 Provider；流式响应已提交后，透明切换会导致内容拼接或重复，通常只能返回流内错误。[S46]

工具调用、支付、写数据库等非幂等操作，应依赖业务幂等键和状态机，而不是“换模型再试一次”。

研究演进：从级联到受约束在线学习

主线是逐步解决完整反馈昂贵、模型池变化、预算约束和 Agent 延迟奖励。

2023级联与自验证

FrugalGPT 学习模型级联；AutoMix 用小模型生成、自验证，再决定是否升级。论文降本比例受数据集、价格和质量阈值影响，不能直接外推。[S31][S32]

2024偏好路由与统一基准

RouteLLM 用偏好数据学习强弱模型路由；RouterBench 提供约 40.5 万条结果，开始统一比较成本—性能曲线。[S33][S34]

2025简单基线与开放竞技场

研究发现调优 kNN 可能超过复杂 Router；RouterArena 扩展领域、难度、商业 Router 和多维指标。[S36][S37]

2026大规模、在线、SLA 与 Agent

LLMRouterBench 扩展到 21 个数据集、33 个模型；SLARouter、WISERouter、OrcaRouter探索稀疏反馈、预算约束和 Bandit；TRACE 与 TwinRouterBench 推进到 Agent 任务/轨迹。[S35][S38][S39][S40][S41][S42]

离线全信息 vs 在线部分反馈

离线：同一 Prompt 调所有候选并评分，比较公平，但成本随请求数 × 模型数增长，且容易与生产分布偏离。

在线：只观察被选择模型，更贴近现实，但存在选择偏差、稀疏奖励与安全探索问题。

Agent 改变了路由单位

逐请求换模型会破坏 Prompt Cache、工具格式兼容，并使终局奖励难归因。

TRACE-Router 倾向任务入口选一次并固定模型；TwinRouterBench 强调真实轨迹中的中间调用。[S38][S42]

不要迷信论文中的降本百分比结果依赖候选模型价格、输出长度、评测集、质量阈值、Judge、缓存、重试与时间点。应该复现方法，不是复制数字。

推荐的生产架构

Gateway 热路径保持稳定，Router 策略独立迭代，反馈训练异步进行。

控制面 · Control Plane

Model Registry
版本、价格、上下文、模态、工具、区域、协议、合规
Policy & Router Registry
候选池、硬约束、权重、阈值、模型版本、回滚
Evaluation Studio
数据集、Verifier、Judge、人评、Pareto 曲线、切片
Budget / Governance
租户预算、质量下限、数据驻留、审计与审批
↔

数据面 · Data Plane

Protocol Adapter → 请求归一化与能力抽取
Hard Filter → 合规 / 上下文 / 模态 / 工具 / 健康 / 配额
Router Service → 规则 + kNN/GBDT/小模型 + 可选 Bandit
Provider Router → EWMA、成本、限额、缓存粘性、Fallback
Inference Router → Queue / GPU / KV Prefix / LoRA Adapter
Trace & Feedback → 原因、成本、时延、结果、终局成功

Gateway：确定性与可靠性

协议、鉴权、限流、预算、硬过滤、超时、熔断、Provider 路由和日志。

Router Service：可迭代决策

意图、难度、质量预测、效用计算和探索策略；独立版本化与 Shadow。

Feedback Plane：异步学习

收集终局成功、Verifier、成本和用户反馈，重算模型画像，不阻塞请求。

工程原则确定性过滤尽量进程内完成；学习型 Router 必须有超时、默认模型、特征缓存和一键冻结。Router 本身不能成为新的单点。
7

评测体系：证明“省钱而不降质”

价值不是预测某个标签，而是在约束下形成更优的质量—成本—时延前沿。

业务 / 任务质量测试通过、问题解决、转化、事实正确率、人评
经济性每成功任务成本、缓存后成本、重试与人工复核
用户时延Router overhead、TTFT、TPOT、p95/p99、任务完成时长
稳定性错误、Fallback、超时、限额、Route churn、SLA
路由最优性Oracle gap、regret、Pareto domination、预算遵守
安全与合规非法候选率、数据驻留、敏感任务探索率、审计
缓存效率Prompt/KV Cache 命中率、粘性收益、切换损耗
可解释性reason 覆盖、回放率、策略与模型版本可追踪

必须保留的四个基线

Strong-only

所有请求走最强候选，作为质量上界与成本基线。

Cheap-only

所有请求走最便宜候选，作为成本下界与质量风险基线。

Random / Fixed Mix

验证收益不是单纯改变流量比例。

Rules / kNN

复杂 Router 必须显著超过简单可解释基线。

四阶段验证

阶段做法关键问题退出条件
Offline Replay历史请求对候选生成/回放，用 Verifier、人评或 Judge。是否形成更优 Pareto 曲线？质量下限内显著优于简单基线。
Shadow现网照常执行，新 Router 旁路给出选择。分布漂移、估计与真实是否一致？覆盖、SLO、错误与审计稳定。
Canary / A-B低风险流量小比例执行，保留现状 Holdout。业务 KPI、尾延迟、缓存与重试是否改善？置信区间过门槛且无合规异常。
Constrained Online仅在安全候选与预算内探索。能否适应价格、版本和流量漂移？Regret、预算和质量长期稳定，可冻结回滚。
反馈优先级真实任务成功 / 单元测试 / 业务结果 ＞ 确定性 Verifier ＞ 专家人评 ＞ 多 Judge 共识 ＞ 单一 LLM Judge ＞ 点赞、停留时长等弱信号。

按场景选择路由配方

先看反馈是否可验证、任务是否多轮、失败是否可逆。

高并发问答 / RAG
意图与风险硬过滤；简单问答走轻量模型，低置信度升级；Session 保持模型/Provider 粘性。
hard filter → intent/complexity → cheap/strong → verifier/escalate → cache affinity
Coding Agent
工具与上下文先过滤；任务级固定模型，用测试/构建/Issue 解决率做奖励。
task admission → pin model → tools/tests → terminal reward → update
抽取 / 分类
通常规则或小模型足够；用 JSON Schema/正则验证，失败再升级。
small model → deterministic verifier → one retry / strong fallback
长上下文 / 多轮
窗口和缓存能力先做硬约束；比较缓存后的成本与 TTFT，避免每轮换模型。
context filter → session pin → provider sticky → prefix-cache-aware pod
高风险决策
固定验证过的模型子集，关闭或限制在线探索；增加 Guardrail、人审和审计。
policy allowlist → quality first → verifier / human → immutable audit
批量离线任务
采用批级预算和抽样质检；按整批质量与总成本优化。
batch segment → budget allocate → cheap tier → sampled QA → selective rerun

面向自研 AI Gateway 的接口设计

把智能路由做成可插拔 Pipeline，而不是写死在核心代理逻辑里。

内部接口

type Router interface {
  Name() string
  Decide(ctx context.Context, in RouteInput) (RouteDecision, error)
}

type RouteDecision struct {
  Model ModelID
  Provider ProviderID
  ReasonCodes []string
  Estimates UtilityEstimate
  PolicyVersion string
  Fallbacks []RouteTarget
}

插件顺序

normalize
  → capability_filter
  → compliance_filter
  → session_affinity
  → task_router
  → utility_optimizer
  → provider_balancer
  → executor
  → retry_fallback_policy
  → trace_feedback

对外 API

字段作用原则
model: auto/balanced调用方声明优化意图，而非绑定模型。保留固定模型入口，便于回归、审计和强制路由。
routing_policy选择策略版本或租户策略。服务端可禁止覆盖；策略必须版本化。
quality_floor / cost_budget / latency_slo表达约束而非权重。约束比单一权重更易审计。
session_id用于模型/Provider 粘性和缓存。不以敏感原文为键；设置 TTL 和故障解除。
route_debug测试环境返回候选打分和过滤原因。生产只返回安全 reason code。
推荐 MVP第一版只做 Model Registry + Capability Filter + Provider HA + 规则/意图 Router + 完整 Route Trace；第二版接 kNN/GBDT；第三版再开放受约束在线学习。

十个常见误区

多数失败不是算法不够先进，而是优化对象、反馈和工程边界定义错误。

1. 把负载均衡叫模型智能路由

选 Provider 与选模型的价值不同，应分开评测。

2. 直接用 Prompt 长度当难度

长文本可能是简单总结，短题也可能需要深推理。

3. 先打分，后检查能力

工具、模态、上下文、地域必须先硬过滤。

4. 只看每百万 Token 价格

输出长度、重试、缓存和成功率会改变真实成本。

5. 只用公开 Benchmark 训练

价值来自模型在你的流量上的互补性。

6. 用一个 LLM Judge 当真相

Judge 有模型、长度和领域偏好，应与 Verifier、人评交叉。

7. 多轮每轮重新选模型

会损失缓存并产生消息/工具格式兼容问题。

8. 流式输出中随意 Fallback

首 Token 后难无缝切换，需设计可识别的流内错误。

9. 对工具写操作盲目重试

非幂等副作用应由业务幂等和状态机保障。

10. 不记录策略和模型版本

无法回放“为什么选它”，就无法定位质量回退。
