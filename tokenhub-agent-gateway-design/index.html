PR #196 · A2A 1.0 · 设计全景

从模型网关，走向 Agent 运行治理平台

这份页面从第一性原理总结 TokenHub Agent Gateway 的完整设计思想： 为什么 Agent 不能按普通 HTTP 请求治理，以及如何用 Agent、Instance、Task、Execution、Delegation 与 Budget 构建一个可发现、可授权、可路由、可追踪、可控成本的执行平面。

设计对象：TokenHub A2A Agent Gateway 协议：A2A 1.0 JSON-RPC / SSE 快照日期：2026-08-23
核心命题：Agent 网关不是“再加一个转发接口”，而是把无状态 API 网关升级为 有状态的任务路由器 + 分布式执行治理器 + 安全委托控制面。

01第一性原理：为什么普通网关不够

模型调用通常是一次性计算；Agent 调用则可能跨分钟、跨服务、跨工具，并产生不可逆副作用。 所以治理单元必须从“请求”上移到“任务与执行”。

传统模型网关

单次、无状态、可重试

请求 → 模型 → 响应
路由单位：HTTP Request
失败策略：换实例重试
成本单位：单次 Token
→
Agent 网关

长程、有状态、有副作用

发现 → 授权 → 执行 → 续接
路由单位：Task / Execution
失败策略：优先避免重复副作用
成本单位：完整调用图
决定架构的关键事实 “请求超时”不等于“上游没有执行”。创建工单、发邮件、修改代码等操作若盲目切换实例重试，可能造成重复副作用。

02整体架构：控制面与数据面分离

控制面负责定义“谁、可以用什么、部署在哪里”；数据面负责每次调用的身份、授权、路由、状态与预算。

03核心对象：把复杂性放在正确的位置

设计的关键不是表多，而是让每个对象只回答一个问题，从而避免把服务、部署、任务和执行链混成一团。

Agent稳定的逻辑服务身份
Revision可审计、可回滚的配置版本
Skill可发现、可单独授权的能力
Instance真实部署、凭据与容量
Task一次有状态交互与上游亲和
Task Event流式状态和产物增量
Execution完整 Agent 调用链沙箱
Edge / Step调用图中的单次边
Usage模型、MCP、Agent 成本记录
Lease跨副本并发占用凭证
Access Binding默认拒绝的授权规则
Access Group可复用的主体集合
Agent = “服务是什么” ； Instance = “部署在哪里” ； Task = “这件事进行到哪” ； Execution = “整个调用图发生了什么”

04七条核心设计原则

①

Agent 不是一个 URL

调用方只依赖稳定 Slug；部署地址、静态凭据、权重、优先级与容量属于 Instance。这样才能做多实例、灰度、回滚和故障隔离。

②

发现本身就是授权

无权限者不仅不能调用，也不应知道 Agent 或 Skill 是否存在。缺失、未认证和未授权尽量返回同样的非披露结果，阻断能力枚举。

③

Task 是有状态路由，不是普通负载均衡

首次请求选择实例；后续 Get、Cancel、Subscribe 与 continuation 必须回到同一实例。Task ID 在网关侧做映射，隐藏真实上游标识。

④

Execution 是分布式 Agent 的运行沙箱

它聚合 Agent Hop、模型调用、MCP 调用、Token、成本、并发与 Deadline，使预算约束能够跨进程、跨 Agent 持续生效。

⑤

Delegation Token 是“可续接能力”

短期 Token 同时携带身份、Execution、Trace、父 Step、深度、调用链和 Deadline。它不是普通 API Key，而是受限的 continuation capability。

⑥

A2A 是主协议，Responses 是兼容层

内部只保留一套 Agent 治理逻辑。Responses 请求先转换为 A2A Message，结果再映射回 Responses，降低现有客户端的接入成本。

⑦

安全不是外围插件，而是执行路径的一部分

身份、Skill 授权、SSRF、防 DNS Rebinding、Header 白名单、输入/输出 Guardrail、任务归属与加密凭据必须串在同一条调用链上。

05运行机制：一次请求如何被治理

5.1 首次调用：选择并租用 Instance

候选实例 = Active ∩ 可用健康状态 ∩ 未超并发
选择顺序 = 最高 Priority 组 → 按 Weight 加权随机 → 低优先级兜底

优先级

表达主备关系。高优先级未耗尽时，低优先级不参与竞争。

权重

表达同等级流量比例，例如 80/20 灰度或异构容量分配。

Lease

数据库原子占位，进程崩溃后由过期 Lease 回收，避免并发数永久泄漏。

5.2 后续调用：Task Affinity

为什么不自动切换实例？ Agent 可能已执行了有副作用操作。对 continuation 重新负载均衡，无法保证语义一致，也可能造成重复执行。

5.3 长任务：Execution 必须保持存活

SendMessage 返回 SUBMITTED / WORKING Root Execution 与对应 Step 保持 running，不提前结算。
上游继续使用 Delegation Token 后续 Agent、模型和 MCP 调用仍进入同一 Trace 与预算域。
GetTask / SubscribeToTask 恢复上下文 恢复原 Execution、Trace、Deadline、Chain 和父 Step，而不是创建第二个根执行。
任务进入终态 完成对应 Step，并将 Root Execution 结算为 completed / canceled / failed。

5.4 Snapshot + Event：兼顾读性能与完整历史

Snapshot

提供 List/Get 的快速读取，持续折叠状态消息、历史消息与 Artifact 分片。

Event

保留有序增量，用于审计、调试、SSE 续接与未来的事件重放。

5.5 Execution Budget：对完整调用图设边界

预算约束对象目的
max_agent_hopsAgent → Agent 深度/总边数阻止递归爆炸与复杂度失控
max_model_calls委托模型调用限制循环规划和隐性成本
max_mcp_calls工具调用限制副作用与外部系统压力
max_tokens模型 + MCP 汇总 Token控制计算与上下文消耗
max_cost_usdAgent 固定成本 + 模型/MCP 成本提供硬成本边界
max_concurrencyExecution 内运行中的 Edge抑制并行扇出
deadline完整 Execution统一长任务生命周期上限

06安全模型：零信任式 Agent 调用链

每一跳都重新验证主体、能力、归属与预算，不能因为请求来自另一个 Agent 就默认可信。

授权维度

Global、Team、Project、API Key、End User、Calling Agent、Access Group，并支持 Skill 级规则和 Deny 优先。

凭据隔离

上游静态 Header 加密存储；Agent Card 对外不暴露内部 URL 与凭据；客户端 Header 仅按白名单转发。

网络安全

生产环境要求 HTTPS，注册时和拨号时都检查特殊地址，阻止私网、回环、CGNAT、保留地址与重定向绕过。

循环保护

Delegation Token 携带 Agent Chain 与 Depth；出现 A → B → C → A 或超深调用时立即拒绝并结束 Execution。

07Responses 桥：兼容现有生态，但不伪装成完整 A2A

model: "agent/<slug>" 让只理解 OpenAI Responses API 的客户端也能调用 Agent； 但桥接必然是有损映射，因此必须明确输出优先级和非终态语义。

08关键权衡与能力边界

设计选择获得代价 / 边界
Task 固定实例，不盲目 Failover 避免重复副作用，保持上游状态一致 实例彻底丢失时恢复能力较弱，需要上游持久化或业务补偿
A2A 1.0 单协议 实现边界清楚，减少兼容分支 不满足旧版 A2A 0.3 客户端，需要独立兼容层
Responses 作为薄桥 现有 SDK 几乎零改造接入 复杂 Artifact、交互状态和异步生命周期无法完整表达
MCP 由 Agent 主动上报 无需代理所有工具协议，接入简单 属于协作式治理，不能强制观测 Agent 内部全部调用
Snapshot + Event 双写 读取快，同时保留增量历史 必须保证折叠逻辑、序列号和事务一致性
数据库承载预算与 Lease 跨副本一致，崩溃后可恢复 高并发时数据库成为关键协调点，需要索引与竞争治理

09当前可增强的地方

下面按“合并阻塞 → 正确性 → 生命周期 → 产品语义”排序。先解决结构性问题，再扩展能力。

P0同步最新 main，并适配正式 Migration Framework PR 与主干已长期分叉。数据库模型、路由与 CI 继续变化前，应先完成重基或合并，避免在旧 AutoMigrate 体系上叠加新表结构。
P1将 Usage Step 唯一性改为 (execution_id, step_id) step_id 应在一个 Execution 内唯一，而非全局唯一；否则不同执行复用 mcp-step-1 会产生冲突。
P1MCP 计量接口复用完整 Delegation 校验 除签名与过期时间外，还应校验 API Key、Project、Execution 状态、Caller Agent、Task 归属与 End User 隔离。
P1补齐 Task / Event / Execution 保留与清理策略 为过期任务设置 TTL，增加批量清理与 Deadline Reconciler；审计数据可分层保留，避免运行表无限增长。
P2明确非终态 Task 到 Responses 的语义 可选择同步等待终态、返回 incomplete 并暴露查询 ID，或明确拒绝非终态；不能把 SUBMITTED / INPUT_REQUIRED 统一标记为 completed。
P2将被动健康冷却演进为可配置熔断策略 区分协议错误、业务错误、超时和网络错误；增加半开探测、窗口失败率与实例级可观测指标。

10建议的演进路线

Phase 1 · 可用

统一 Agent 接入

  • A2A 1.0 JSON-RPC / SSE
  • Agent Registry 与 Card
  • 默认拒绝授权
  • Task Affinity 与多实例路由
  • Responses 兼容桥
Phase 2 · 可靠

生命周期与一致性

  • 正式数据库迁移
  • 复合 Step 唯一性
  • Task / Execution Reconciler
  • 完整委托鉴权
  • 事件续接与幂等策略
Phase 3 · 平台化

可运营的 Agent 控制面

  • 策略化预算与租户配额
  • 主动健康探测与熔断
  • 执行图检索与成本归因
  • 审批、风险分级与补偿流程
  • 更完整的协议与异步桥接
最终形态不是一个“A2A 代理”，而是： Agent Registry + Stateful Gateway + Execution Governance + Security Delegation + Cost Control。
