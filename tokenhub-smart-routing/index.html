Executive summary

方案结论

在 TokenHub 现有基础设施路由之前，新增独立的 Smart Model Router / Capability Routing Plane。它只回答“这一请求或这一回合应该使用哪个逻辑模型”，然后将结果交给 TokenHub 当前的 Provider 路由继续执行。

最重要的架构边界

智能模型路由选择 effective_model；TokenHub 现有路由选择 Provider、账号与资源实例；Agent Runtime / Eval判断任务最终是否成功。

独立路由层

不把 Stage Router 塞入现有 ModelRoute.Strategy，避免模型选择与 Provider 排序职责混淆。

强模型可信兜底

低置信、协议不兼容、状态不可迁移、高风险工具与路由故障，默认进入 capable target。

结果驱动评测

不以小模型调用比例为目标，以质量保持、LOSS 率、每成功任务成本和端到端时延为准。

Scope & boundaries

设计目标与边界

目标
  • 支持静态条件、请求语义与 Agent 轨迹级路由。
  • 具备 observe、shadow、enforce 和一键回滚。
  • 让每次决策可解释、可重放、可关联最终 Outcome。
  • 兼容 Chat Completions、Responses、Anthropic Messages。
  • 完整复用 TokenHub 的鉴权、配额、预算、审计与 Provider Failover。
非目标
  • 不允许路由器动态生成任意 Endpoint 或读取 Provider Credential。
  • 不允许策略执行任意脚本或动态下载未签名模型工件。
  • 第一期不做流式响应中的弱模型回答后撤回重做。
  • 不自动覆盖客户端显式请求的普通 Physical Model。
  • 不将图像、语音、Embedding 与 Chat 模型混为同一候选组。

Routing engine

推荐算法：规则 + Stage + 模糊区间分类器

第一版不需要复杂训练系统。结构化 Agent 轨迹配合确定性规则与可校准阈值，就足以构建可解释、低延迟的生产 MVP。

Session-aware routing

会话状态与模型切换

逐回合独立分类会造成 efficient ↔ capable 抖动、缓存损失和工具上下文断裂。生产实现需要 Session Hysteresis 与 Hard Lock。

Hard lock

工具调用闭环

模型 A 发出 Tool Call 后，Tool Result 优先返回模型 A，避免另一个模型缺失局部意图。

Hard lock

Provider-managed State

存在 previous_response_id、Reasoning Signature 或不可移植 Session Token 时保持原状态域。

Hard lock

Streaming 已提交

首字节发送给客户端后禁止跨模型切换；模型 fallback 只能发生在提交之前。

非对称 Hysteresis

升级宽松，降级严格

出现错误可以立即升级 capable；从 capable 降回 efficient 则需要 Hold 到期、连续 clean/progress 回合以及更高置信度，从而减少模型抖动。

if criticalError {
    return CapableWithHold(2)
}
if currentTier == Efficient && score >= upgradeThreshold {
    return CapableWithHold(2)
}
if currentTier == Capable && holdExpired &&
   cleanTurns >= requiredCleanTurns &&
   score <= -downgradeThreshold {
    return Efficient
}
return currentTier

Evaluation loop

效果评测：在线记录，离线证明

路由分数不能自证正确。在线链路只负责决策、执行和记录；真正的效果判断来自 Benchmark、Shadow、A/B 与最终 Task Outcome。

核心评价目标

在业务允许的质量下降范围内，最小化 Cost Per Success 与端到端任务时长，而不是最大化 efficient 模型流量。

三组基线与四象限

同一批任务至少运行 capable-only、efficient-only 和 routed；必要时增加 random 作为“路由算法增益”基线。

SAFE

capable 成功，efficient 也成功。适合交给高效模型，是主要降本空间。

LOSS

capable 成功，但 efficient 或 routed 失败。最危险的误降级，必须单独设红线。

RESCUE

capable 失败，efficient 成功。反映模型互补、随机性或特定能力差异。

HARD

两者都失败。应改进 Harness、工具、上下文或引入更强模型，而非只调阈值。

核心指标

指标定义用途
Quality RetentionRouted 成功率 / Capable-only 成功率衡量能力保持
Cost Per Success全部模型、Classifier、重试与 Shadow 成本 / 成功任务数核心经济指标

Task Duration任务开始到最终 Outcome 的 P50 / P95 / P99防止便宜模型制造长错误轨迹

Cache & Switch缓存命中变化、模型切换次数衡量跨模型隐性成本

Observe、Shadow、Enforce 的差异

Observe

只计算假想决策

真实请求始终发给 capable。可验证分布与可解释性，但不能证明 efficient 真能完成。

Shadow

后台执行反事实

采样复制给 efficient，结果不返回用户。必须禁止具有外部副作用的工具。

Enforce

真实采用路由结果

仅在离线回放、Shadow 与质量 Guardrail 通过后，对低风险任务逐步放量。

MVP 验收标准

  • Physical Model 请求完全兼容

  • 非法 Target 选择率为 0
  • 路由异常 100% 可信兜底
  • Streaming 首字节后跨模型切换为 0
  • 每次决策可追溯到精确 Policy Version
  • Session 不跨租户或版本共享
  • Observe 可复现同一输入的决策
  • 具备 capable / efficient / routed 对照报告
